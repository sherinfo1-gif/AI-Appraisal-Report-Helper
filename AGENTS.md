# AI Report Helper Agent Instructions

These instructions apply to the entire repository.

## Repository Boundaries

- `prototype/` is a static discovery prototype. It validates navigation,
  terminology, information hierarchy, and visual design. Do not import
  production modules into it or treat its hard-coded values as business rules.
- `src/`, `public/`, and `test/` contain the experimental production-oriented
  foundation. It is not yet a certified production system.
- `docs/` contains architecture and product decisions. Read the relevant
  document before changing a domain boundary.
- `data/` is local runtime storage and must remain untracked.
- Source reports, workbooks, and standards are discovery inputs. They do not
  define approved formulas or production methodology.

## Domain Invariants

- `ValuationCase` is the aggregate root for an appraisal engagement. Assignment
  data, asset groups, evidence, calculations, report sections, reviews, and
  releases belong to that case.
- Mixed-property work is represented by one `ValuationCase` with independent
  asset groups. Do not merge completed Word reports as the primary data model.
- Workflow profiles, object definitions, templates, methodology, calculation
  models, and report sections are versioned. Existing cases remain pinned to
  the versions they were created with unless an explicit migration is designed.
- Material actions are recorded in an append-only audit trail. Never update or
  delete historical audit events to hide a later correction.
- OCR, AI, imports, and calculated narratives are proposals until an authorized
  appraiser explicitly accepts them. Automation must not silently replace
  manual report text.
- Issued releases are immutable snapshots. A correction creates a new numbered
  release and does not modify the previous release.

## Storage And Confidentiality

- Customer documents, addresses, photos, workbooks, calculations, and reports
  stay on company-controlled infrastructure.
- Do not send repository or case data to external services without explicit
  approval and an implemented anonymization boundary.
- Never commit API keys, credentials, local databases, uploaded documents,
  generated releases, logs, or backups.
- Real customer data must not be used as demo or test fixtures. Use clearly
  fictional and non-identifying data.

## Methodology And Demo Safety

- Do not convert prototype values, demo coefficients, example formulas, or
  supplied workbooks into production logic.
- Do not introduce valuation formulas without methodologist approval,
  documented sources, and golden-case tests.
- Demo screens may illustrate a workflow but must be labeled and isolated from
  production services and persistent production decisions.
- Legal or methodological wording generated by automation requires source
  attribution and human approval.

## Change Discipline

- Keep prototype and production-oriented changes in separate commits.
- Do not remove or substantially redesign existing prototype screens unless the
  task explicitly requests it.
- Do not push directly to `main`. Work in a feature branch and submit changes
  for review.
- Preserve unrelated user changes in a dirty worktree.
- Keep changes scoped; do not add backend, database, OCR, AI, document
  generation, or valuation formulas to repository-hygiene tasks.
- Update `CHANGELOG.md` under `Unreleased` for material repository or product
  changes.

## Commands

Requirements: Node.js 24 or newer.

```powershell
# Production-oriented foundation
node src/server.js
node --test

# Static discovery prototype
python -m http.server 4180 --bind 127.0.0.1
```

Open the prototype at `http://127.0.0.1:4180/prototype/`.

## Verification

- Documentation-only work: check links, paths, terminology, and repository
  boundaries.
- Prototype work: test basic navigation and inspect the browser console.
- Foundation work: run `node --test` and the relevant browser scenario.
- Report any check that could not be run; do not claim unverified behavior.
